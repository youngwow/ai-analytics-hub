# План развития backend ai-analytics-hub (2026-09-05)

Анализ функционала и рекомендации по развитию. Ничего не менялось — только
документ. Зафиксированные дефекты (курсор `order=priority/processed`,
валидация enum-полей, атомарность транзакций, гонки прогонов) описаны в
`docs/backend-review-2026-09-05.md` и здесь не повторяются: этот документ — про
развитие, а не про починку. Оценки: S (дни), M (1–2 недели), L (больше месяца).

Общий принцип: почти всё перечисленное ниже уже реализовано в `src/cli.py`
(39 команд) и в сервисах — задача не «придумать фичу», а выставить готовое
ядро через HTTP и доделать то, что осталось полуавтоматическим. Слои уже
построены так, что CLI и API сидят на одном ядре (`FeedQuery`, `FeedService`,
`SourceService`, `Collector`, `ProcessingService`), поэтому большинство фич —
это роут + request/response-схема поверх существующего метода сервиса.

## 1. API (src/api/)

### 1.1. Единый контракт фильтрации/сортировки/поиска на /documents

- **Мотивация.** `GET /items` и `GET /items/facets` делят одну форму
  (`FeedQuery`), а `GET /documents` — свою урезанную (`DocumentQuery`): поиск
  там — `LIKE '%q%'` без экранирования (`src/repositories/feed.py:285-287`),
  сортировки нет, `order` не поддерживается. Дашборд «сырых документов» не
  может отсортировать по `fetched_at` или найти по подстроке надёжно.
- **Слои.** `src/repositories/feed.py`, `src/models/queries.py`,
  `src/api/query.py`.
- **Размер.** S.
- **Риски.** Низкие: маршрут новый контракт не ломает; добавить `order` —
  обратно-совместимое расширение (дефолт прежний).
- **Зависимости.** Нет.

### 1.2. Bulk-теги и bulk-архивация карточек

- **Мотивация.** Единственная массовая операция — `POST /items/bulk`
  (видимость под дайджест, `src/api/routes/items.py:82-85`). Массовый тегинг —
  регулярная работа аналитика («пометить 20 карточек тегом КИИ»), сейчас он
  возможен только 20 одиночными PATCH. Массовая архивация (после отправки
  дайджеста) — тот же сценарий, но её нет даже в CLI.
- **Слои.** `src/models/requests.py`, `src/api/routes/items.py`,
  `src/services/item_service.py`, `src/repositories/items.py` (паттерн
  `set_visibility_bulk` уже есть — повторить для тегов и `is_archived`).
- **Размер.** S.
- **Риски.** Низкие: новый эндпоинт `POST /items/tags/bulk`, существующие
  контракты не трогает. Не забыть пересборку `items_search` после смены тегов
  (тег входит в строку индекса).
- **Зависимости.** Нет.

### 1.3. Экспорт среза: RSS/Atom и CSV

- **Мотивация.** Дайджест уже умеет markdown и JSON (`POST /digest`), но
  забирает его человек через дашборд. RSS-выход (`GET /feed.xml` по тем же
  `FeedQuery`-фильтрам) закрывает сценарий «подписать руководителя/соседний
  отдел на живую ленту», CSV — «отдать срез в Excel для отчёта». Оба —
  честное расширение того же среза, отдельного ядра не требуют.
- **Слои.** Новый роут `src/api/routes/export.py`; сериализация поверх
  `FeedService.items()`; для CSV — ручной writer (зависимостей нет).
- **Размер.** S (CSV) + M (RSS: нужно решить, как в RSS-элемент попадает
  `visibility`/`archived` — фильтр по умолчанию должен повторять дайджестный:
  только `visible`).
- **Риски.** Средние: RSS — это публичный канал по сути; без авторизации
  (вне скоупа) отдавать можно только не-`hidden` срез и без `analyst_note`/
  заметок. Версионирование не нужно: это новые GET-эндпоинты.
- **Зависимости.** Нет.

### 1.4. Идемпотентность и Idempotency-Key на мутирующих эндпоинтах

- **Мотивация.** `POST /items` (ручной материал) при повторе по таймауту
  создаёт второй документ — частично спасает `_find_duplicate` + `force=False`,
  но только внутри окна SimHash и только при совпадении URL/текста.
  `POST /processing/runs` и `POST /collection/runs` защищены 409-проверками,
  но check-then-insert (см. аудит) — двойной клик может пройти. Заголовок
  `Idempotency-Key` с таблицей `idempotency_keys(key, endpoint, response)`
  делает повтор безопасным на контрактном уровне.
- **Слои.** middleware/зависимость в `src/main.py`, миграция v6, все POST.
- **Размер.** M.
- **Риски.** Низкие: опциональный заголовок, старые клиенты не меняются.
- **Зависимости.** Устраняет зависимость от починки гонок из аудита, но не
  заменяет её: сделать и то, и другое.

### 1.5. Выставить профиль компании через API

- **Мотивация.** Приоритеты считает профиль (`profile.resolve`,
  `src/processing/profile.py`), но его CRUD есть только в CLI (`profile
  show/list/use/set`, `src/cli.py:1416-1429`). Смена профиля = смена того, что
  считается `high` — это операция владельца продукта, не того, кто ходит в
  терминал. `ProcessingRunRequest.profile_id` уже приходит в API — но задать
  или хотя бы посмотреть доступные профили из API нельзя.
- **Слои.** `src/api/routes/` (новый `profiles.py`), `ProfileRepo`
  (`src/repositories/processing.py`) — готов, добавить только GET-ы, затем
  POST/PATCH с версионированием (`ProfileRepo.save` уже версирует).
- **Размер.** S (read-only GET) → M (CRUD + защита инварианта «версия = строка
  истории»).
- **Риски.** Низкие: GET ничего не ломает; на запись — учесть, что профиль
  попадает в промпт, т.е. запись = управление промптом.
- **Зависимости.** Нет.

### 1.6. Выставить quality-сводку через API

- **Мотивация.** `quality_summary` (`src/services/processing_service.py:715`)
  — единственный агрегат честного качества (деградация, доля правок, токены,
  частота отказов модели) — доступен только через `python -m src quality`.
  Дашборд «качество модели» без него требует прямых SQL-запросов.
- **Слои.** Роут `GET /processing/quality` поверх существующего метода.
- **Размер.** S.
- **Риски.** Нет: read-only, контракт — расширение существующего префикса.
- **Зависимости.** Нет.

### Отдельно отмечённое, что НЕ предлагаю

- Пагинация с курсором «везде»: она уже есть в обоих списочных эндпоинтах
  (`/items`, `/documents`), включая общий fingerprint среза; чинить нужно
  только баг `order=priority/processed` (аудит, п. 1), новой фичи не требуется.
- PATCH для источников: уже есть (`PATCH /sources/{id}`, включая переезд на
  другой адрес с ресолвом и сбросом курсора).

## 2. Сервисы (src/services/)

### 2.1. Повторный прогон сбойных документов (retry-failed)

- **Мотивация.** Прогон обработки считает `report.failed`
  (`processing_service.py:243-245`), но «провалившиеся» нигде не
  персонализированы: документ без карточки, который упал в этом прогоне,
  ничем не отличается от «ещё не брался» — кроме записи в логе. Операция
  «повторить только сбойные» существует только в виде «запустить прогон
  заново и надеяться». Нужно: таблица или колонка `documents.last_error` +
  фильтр `unprocessed(only_failed=True)` и параметр прогона.
- **Слои.** `src/repositories/documents.py` (`unprocessed`), миграция,
  `ProcessingService._run`, параметр в `ProcessingRunRequest` и CLI `process`.
- **Размер.** M.
- **Риски.** Низкие: новый необязательный параметр прогона — обратно
  совместимо.
- **Зависимости.** Нет; но приятнее после устранения гонок прогонов.

### 2.2. Устранить двойное хранение заметки аналитика

- **Мотивация.** Миграция v3 перенесла `items.analyst_note` в `item_notes`,
  но CLI `edit --note` (`src/cli.py:795`) продолжает писать в колонку, а
  `EDITABLE_FIELDS` включает `analyst_note`. Устаревший флаг API — CLI
  `note`, HTTP — `notes`. Один источник правды: `item_notes`.
- **Слои.** `src/services/item_service.py`, `src/cli.py`, миграция-чистка
  (перенос остатков из колонки в `item_notes` по образцу v3, затем — не
  трогать колонку).
- **Размер.** S.
- **Риски.** Низкие: в HTTP контракт не входит (`ItemUpdateRequest` поля не
  имеет). CLI-флаг помечаем deprecated и оставляем как alias на 1 версию.
- **Зависимости.** Нет.

### 2.3. Убрать двойной FTS-индекс и мёртвый путь `items_fts`

- **Мотивация.** В схеме два FTS-индекса: рабочий `items_search` (v4) и
  `items_fts` (v2) с тремя триггерами на каждый INSERT/UPDATE/DELETE —
  второй обслуживает только недостижимый `SqliteItemRepository.list(query=)`
  (см. аудит). Это не «пересборка FTS вручную», а удаление балласта: триггеры
  впустую удорожают каждую запись карточки, а санитайз `to_match()` не
  применяется на мёртвом пути.
- **Слои.** Миграция v6 (`DROP TRIGGER` × 3, `DROP TABLE items_fts`),
  `src/repositories/items.py`, `repository_interface.py`.
- **Размер.** S.
- **Риски.** Низкие: убрать интерфейсный метод и реализацию одновременно;
  внешних потребителей нет (тесты обновить).
- **Зависимости.** Нет.

### 2.4. Полуавтоматические операции, прослеженные в ядро

Коротким списком — уже реализовано и не требует нового ядра, только
выставления/склейки (включено в стоимость соответствующих фич выше):
`SearchRepo.rebuild_all()` вызывается только из миграции — ручная пересборка
индекса доступна лишь SQL'ом; добавить `POST /admin/search/rebuild` (S,
закрыт для внешних, но без авторизации — пусть пока будет доступен только
через CLI-команду). Прогон pipeline по одному документу: `add_manual` умеет,
но «прогнать заново один документ без карточки» = частный случай 2.1.

## 3. БД (src/repositories/)

### 3.1. Индексы под реальные запросы

- **Мотивация.** По аудиту: сортировка ленты идёт по `COALESCE(...)` — индекс
  `idx_items_feed` не используется; `count_unprocessed` — full scan на каждый
  опрос `/status` и `/processing`. Это первые кандидаты, когда объём вырастет с
  сотен карточек до десятков тысяч.
- **Слои.** Миграция v6/v7: expression index
  `ON items(COALESCE(published_at,'') DESC, id DESC)` (+ вариант для
  `processed_at`), частичный индекс для `count_unprocessed`
  (`WHERE hidden = 0` + `NOT EXISTS` нельзя индексом — тогда денормализовать
  колонку `has_card` с обновлением в `link_sources`).
- **Размер.** S (индексы) / M (денормализация `has_card`).
- **Риски.** Низкие: expression-индексы в SQLite работают с 3.9; риск —
  забыть, что `ORDER BY` в `feed_sql` должен буквально совпасть с выражением
  индекса.
- **Зависимости.** Нет.

### 3.2. Механизм миграций: защитить то, что есть

- **Мотивация.** Механизм существует (`_MIGRATIONS` по `PRAGMA user_version`,
  `src/repositories/database.py:440-452`), но `executescript` не атомарен и
  повторное применение падает на «duplicate column» (аудит). Развитие
  минимальное: каждую миграцию в `BEGIN IMMEDIATE ... COMMIT` +
  `PRAGMA user_version` внутри той же транзакции; ALTER'ы защитить по
  `PRAGMA table_info`.
- **Слои.** `src/repositories/database.py` (только `_migrate` и обёртка).
- **Размер.** S.
- **Риски.** Низкие; формат миграций не меняется.
- **Зависимости.** Нет. Эта фича — предпосылка для всех последующих миграций
  (v6+), делать первой.

### 3.3. Полнотекстовый поиск: фразы, морфология, поиск с фасетами

- **Мотивация.** `items_search` (FTS5, `unicode61`) уже даёт префиксный поиск
  с snippet'ами и общими фасетами. Не поддерживает: поиск по фразе в кавычках
  (санитайз `to_match` уничтожает кавычки — осознанно, но «искать точную
  формулировку» нельзя), морфологию (`законопроект*` не найдёт «законопроекта»
  — уже решено префиксами, но «принятие» по «принят» не найдётся), а также
  «морфологический» поиск с фильтрами поддержан. Русский стеммер в FTS5
  есть: `tokenize='snowball russian'` (собран в стандартных сборках с ICU? —
  проверить: в macOS-сборке Python snowball доступен через fts5 с 3.34).
- **Слои.** Миграция v7: либо второй `items_search_morph` (безопасно, A/B),
  либо пересоздание таблицы с новым tokenizer + `rebuild_all`;
  `src/repositories/feed.py` (`to_match` — расширить кавычками-фразами
  как опциональный синтаксис `q="..."`).
- **Размер.** M (A/B-вариант) / L (замена tokenizer'а с полным пересбором).
- **Риски.** Средние: пере-токенизация меняет результаты всех сохранённых
  поисков; `rebuild_all` на больших данных — минуты блокировки записи.
  Совместимость: контракт `q` расширяется, дефолт прежний.
- **Зависимости.** 3.2 (атомарные миграции), 2.3 (сначала убрать `items_fts`).

### 3.4. Конкурентная запись

Покрыто аудитом (гонки `enqueue`/refresh/insert) — как фича развития
предлагается одно: **единая точка захвата слота прогона** (уникальный
partial index на `processing_runs.status='running'` + `BEGIN IMMEDIATE`) —
это единственное изменение схемы, остальное — код. S. Без зависимостей.

## 4. Processing (src/processing/)

### 4.1. Наблюдаемость pipeline: этапы и прогресс прогона

- **Мотивация.** `processing_runs` хранит итоговые счётчики (v5), но во время
  прогона (минуты при concurrency=2 и таймауте 300 с) дашборд видит только
  `status='running'`. Прогресса нет: сколько из `documents` уже прошло S0/S1,
  сколько LLM-вызовов сделано, сколько деградировало. Сценарий: аналитик нажал
  «Обработать очередь» и 10 минут смотрит на кнопку без обратной связи.
- **Слои.** Обновление счётчиков в `processing_runs` по ходу прогона
  (`ProcessingService._run`: `processed` после каждого кластера), поле
  `progress` в `GET /processing/runs/{id}`; `llm_calls` уже пишет всё —
  добавить в `GET /processing/quality` разбивку по `stage`/`status`/суткам.
- **Размер.** S (прогресс) + S (разбивка quality).
- **Риски.** Низкие: UPDATE по ходу прогона — на том же соединении;
  контракт — расширение ответа.
- **Зависимости.** Нет.

### 4.2. Приоритизация очереди обработки

- **Мотивация.** Очередь берётся как `ORDER BY published_at DESC`
  (`unprocessed`), `max_new_per_run=200`. Документ с высоким приоритетом
  домена (НПА из regulator-источника) ждёт вместе со спамом media.
  Порядок должен учитывать категорию источника (`sources.category` уже
  есть: `regulator > media`) — тогда при очереди в тысячи документов
  критичное попадает в ленту первым.
- **Слои.** `src/repositories/documents.py` (`unprocessed`: JOIN с
  `sources`, приоритетный ORDER BY), `ProcessingConfig` (вес категорий).
- **Размер.** S.
- **Риски.** Низкие: меняется только порядок, контракт прогона тот же.
- **Зависимости.** Нет.

### 4.3. Батчинг эмбеддингов и повторное использование

- **Мотивация.** `_embed` уже батчит (`embed(texts)` один вызов на прогон) —
  здесь всё хорошо. Недостающее: `clustered_candidates` декодирует и
  сравнивает векторы в Python при каждом прогоне (`find_match`,
  `dedup.cosine`) — на 2000 кандидатов × 200 документов это 400k cosine в
  чистом Python. Достаточно precompute норм + numpy dot (numpy в deps
  отсутствует — либо добавить, либо кешировать нормы в памяти прогона).
- **Слои.** `src/processing/dedup.py`.
- **Размер.** M.
- **Риски.** Средние: зависимость `numpy` в проекте, которого нет
  (`pyproject.toml`); поведенчески результат не меняется.
- **Зависимости.** Нет.

### 4.4. Честные статусы вместо мёртвых флагов

- **Мотивация.** `needs_review` всегда 0 и `evidence_start/end` всегда NULL
  (аудит, п. 4) — UI показывает флаг, который не срабатывает никогда.
  Предлагается не «доделать S6» (это L с сомнительной ценностью), а
  убрать из ответов API мёртвые поля: честное отсутствие лучше
  неработающего признака. Это обратно совместимо только формально
  (поля исчезают из ответа) — помечать как breaking: выносить в `/api/v2`
  не нужно, поле было всегда `false`/`null` и клиентов ветвиться не могло.
- **Слои.** `src/services/feed_service.py` (`flags`), `src/models/responses.py`.
- **Размер.** S.
- **Риски.** Низкие; OpenAPI-дифф меняется — проверить фронтенд.
- **Зависимости.** Нет.

## 5. Sources (src/sources/)

### 5.1. Per-source расписание с backoff

- **Мотивация.** Расписание есть (`poll_interval` 15m/1h/6h/24h,
  `next_run_at`, планировщик из одного запроса `due()`), но интервал
  константный: падающий источник опрашивается так же часто, как здоровый.
  Автопауза есть частично (`FAILURES_TO_ERROR=5` → статус `error`), но
  `error`-источник продолжают опрашивать с тем же интервалом. Предлагается
  экспоненциальный backoff: `next_run_at = now + interval * 2^min(failures,4)`
  для `error`-статуса. Сценарий: сайт лежит неделю — не дёргать его каждые
  15 минут и не копить `source_runs` вхолостую.
- **Слои.** `src/sources/scheduler.py` (`reschedule` берёт `state`),
  `src/sources/collector.py` (`_persist_result` передаёт `consecutive_failures`).
- **Размер.** S.
- **Риски.** Низкие: `due()` уже берёт всех `active`+`error` — backoff только
  сдвигает `next_run_at`; UI виден через существующий `/status`
  (`stale_sources`).
- **Зависимости.** Нет.

### 5.2. Уставший источник: автопауза

- **Мотивация.** Дополняет 5.1: после N дней в `error` (например,
  `error` + 7 дней + 50 неудач) — переводить в `paused` с `hidden_reason`-
  эквивалентом для источников (`notes`), чтобы `due()` вообще перестал его
  брать. Сейчас единственный способ остановить вечный `error` — руками.
- **Слои.** `src/sources/collector.py` или отдельный проход в конце цикла
  `run()`; `Source`/`FetchState` уже несут всё необходимое.
- **Размер.** S.
- **Риски.** Низкие: источник возвращается штатным `resume` (уже есть).
- **Зависимости.** Приятнее после 5.1 (сначала backoff, потом пауза).

### 5.3. Управление пулом источников через API — уже закрыто

Проверено: `POST /sources` (probe→create→backfill в фоне), `PATCH` (переезд,
интервал, пауза), `DELETE`/`restore`, `refresh`, `health` — конфиг
(`sources.json`) нужен только первично, и CLI `sources seed` существует.
Чего реально не хватает в API: `seed`-импорта и `discover`
(Tavily-поиск кандидатов, `cli.py:1309`): **`POST /sources/discover`** —
единственная CLI-функция без HTTP-представления. S, рисков нет, полезно для
дашборда «предложить источники». Зависимостей нет.

## 6. Инфраструктура

### 6.1. /metrics (Prometheus-текстовый формат)

- **Мотивация.** Метрики считаются ad hoc (`took_ms` в ответах, SQL по
  `source_runs`), но `docs/monitoring.md` сам признаёт: «p95 по запросам
  планируется отдельным middleware», агрегатов нет. Эндпоинт
  `/metrics` + middleware, копящий latency/статусы запросов + экспортер
  готовых счётчиков (unprocessed, llm_available, due_sources, доля degraded)
  закрывает «стартовые алерты» одним хостом без Prometheus-стека.
- **Слои.** middleware в `src/main.py`, новый роут, лёгкая агрегация
  (без зависимости от prometheus-client: текстовый формат тривиален).
- **Размер.** M.
- **Риски.** Низкие: новый read-only эндпоинт; не забыть про CORS и о том,
  что метрики без авторизации видят объёмы данных — приемлемо (авторизация
  вне скоупа).
- **Зависимости.** Нет.

### 6.2. Бэкапы SQLite

- **Мотивация.** Единственная копия данных — `data/hub.db`; WAL-файл рядом;
  в compose том, вне — никакого бэкапа. `sqlite3.Connection.backup()` —
  корректный онлайн-бэкап открытой БД (в отличие от копии файлов при живом
  WAL). Сценарий: перед миграцией, перед деплоем, раз в сутки.
- **Слои.** CLI-команда `python -m src backup` (+ опционально `POST
  /collection/...` не делать: бэкап — операция администратора, CLI
  достаточен), директория `data/backups/`, ротация по количеству.
- **Размер.** S.
- **Риски.** Низкие: backup() блокирует запись коротко; тест на
  восстановимость.
- **Зависимости.** Нет.

### 6.3. Запуск как сервиса

- **Мотивация.** Уже решено: `docker-compose.yaml` (restart: unless-stopped,
  init, healthcheck, non-root) + uvicorn factory. Единственный хвост:
  `--reload` и монтирование `./src` в compose (аудит) — это dev-настройки в
  «прод»-compose. Предлагается split: `docker-compose.yaml` (прод, без
  reload) + `docker-compose.override.yaml` (dev). S, рисков нет.

### 6.4. Миграции при старте

Уже есть и работает (`lifespan` открывает и мигрирует схему до первого
запроса, `main.py:36`). Развитие — только 3.2 (атомарность).
