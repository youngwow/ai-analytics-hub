## Что решается правилами

- **Дедупликация — сначала дёшево.** На сборе отсекается совпадение `(source_id, external_id)` и URL. На обработке — SimHash 64 бита по словесным 3-граммам с расстоянием Хэмминга ≤ 8 (правка-перепечатка даёт 2–4, разные документы — от 18). Правило детерминированное, бесплатное и снимает основную массу перепечаток до любого вызова модели.
- **Семантическая проверка ответа модели.** Схема JSON гарантирует форму, правила — смысл: тип и приоритет из фиксированных списков, саммари ровно 3–5 предложений, `relevance_score` и `confidence` в диапазоне 0–1, теги из белого списка, `evidence_offsets` обрезаются по длине `norm_text`. Проверки опоры на оригинал (S6) в коде нет — удалена.
- **Fail-safe по приоритету.** При `relevance_score` 0.35–0.5 или `confidence < 0.5` приоритет поднимается на ступень и никогда не понижается. Это правило в коде, а не просьба в промпте.
- **Тождество и жизненный цикл НПА.** Карточка склеивается только по нормализованному `npa_key`; статус двигается вперёд по списку «анонс → разработка → внесён → рассмотрение → принят → действует → архив» — сравнение индексов, без модели.

## Где уместна классическая ML-модель

- **Сегодня — нигде, и это осознанно:** размеченных данных нет вообще, а обучать модель на пустом месте дороже, чем сформулировать профиль компании словами в промпте.
- **Первый кандидат — приоритет:** классификация на трёх классах (TF-IDF по `norm_text` плюс логистическая регрессия или градиентный бустинг) как дешёвый предфильтр перед LLM, а не замена (саммари он не даёт).
- **Критерий, когда браться:** накопится порядка 300–500 правок приоритета в `item_revisions` и модель обгонит LLM на золотом наборе по recall на `high`. Оценка объёма — допущение: при ~600 документах в сутки и доле правок ~10 % это недели работы аналитика; факт покажет `edited_share`.

## Где нужны embeddings

- **Кластеризация перепечаток (S1)** — единственное место. Новость, переписанная другими словами в 15 каналах, не ловится SimHash, но ловится косинусом по эмбеддингам; порог 0.86 консервативный — лишняя карточка дешевле потерянного материала.
- **Блокировка кандидатов делает это дешёвым:** сравниваются только окарточенные документы окна 7 дней, поэтому векторный индекс (FAISS, pgvector) не нужен. Косинусы внутри окна считает `numpy`: матрица кандидатов собирается один раз на прогон, строки нормируются заранее, и на документ приходится одно умножение матрицы на вектор. На окне 2000 × 200 документов это 16 с чистого Python против 0,2 с — при том же результате (совпадения и оценки сходятся до последнего разряда). `torch` не нужен: обучения нет, только скалярные произведения. Вектор — `float32` BLOB в `documents.embedding`, считается один раз.
- **Retrieval (RAG) в продукте нет:** карточка строится из одного документа, внешняя база знаний в промпт не подмешивается. Поиск — лексический FTS5, не векторный; семантический режим по тем же векторам — очевидное расширение, но замера пока нет.

## Где нужен LLM

- **Саммари 3–5 предложений и сущности «кто / что / когда / последствия»** — основная задача: человеку нужно за 10–15 секунд решить, читать оригинал или нет.
- **Тип и категоризация:** `НПА` | `Новость`, статус НПА, теги (регуляторика / репутация / конкуренты / тренды / господдержка-льготы).
- **Приоритет относительно профиля компании** с `relevance_score`, `reasoning` и `matched_profile_facets`. Правилами не закрывается: базы правил у заказчика нет, а близость темы не равна релевантности.
- **Один structured-output вызов на кластер (S2–S5):** схема уходит параметром `format` — битого JSON не бывает; смысл проверяется своим кодом.

## Где LLM использовать не стоит

- **Тождество карточки НПА** — только по номеру акта. Склейка по эмбеддингам запрещена: лишняя карточка чинится руками дешевле, чем материал, потерянный в чужой хронологии.
- **Ранжирование и фильтры ленты** — по сохранённым полям (`priority`, `published_at`, теги, FTS5), без вызова модели в рантайме: бюджет ленты < 1 с.
- **Проверка фактов второй моделью-судьёй** — удвоение стоимости и латентности ради того, что ловится сравнением чисел и дат; правило дешевле, но сейчас его нет (S6 удалён), вернуть — открытая задача.
- **Смена статуса НПА назад и необратимые действия** — модель предлагает статус, но понижать его или архивировать по её ответу нельзя.

## Baseline, которые запускаются первыми

- **Экстрактивный лид (реализован, аварийный путь):** первые три предложения оригинала, приоритет «средний», `confidence 0.3`, флаг `degraded`. Он же — нижняя планка: если LLM не обгоняет лид, платить за неё незачем.
- **Приоритет по ключевым словам профиля (планируется):** совпадение с `topics` против `negative_facets`. Дешёвая точка отсчёта для «сколько добавляет LLM».
- **Сравнение — на одном наборе:** baseline → LLM с профилем → LLM после правок промпта. Версия промпта и профиля пишется в карточку (`prompt_version`, `profile_version`), поэтому сравнение честное.

## Как валидировать качество

- **Золотой набор ≈ 100 документов** из уже собранных, стратифицированный по категориям источников: эталонные `type` и `priority` у всех, эталонные саммари у 20, негативный пример «законопроект о поддержке МСП → низкий приоритет». Файл — `tests/fixtures/gold/gold_set.jsonl`. **Код подсчёта готов (`src/processing/quality.py`, `python -m src quality --gold`), набор не размечен** — ближайшая открытая задача.
- **Гейты приёмки:** recall по `high` ≥ 0.95, точность приоритета ≥ 0.80, ноль неподкреплённых утверждений в 20 эталонных саммари. Асимметрия из task.md: пропустить критичное дороже, чем показать лишнее — цель полнота, а не чистота.
- **Регрессия офлайн:** ответы модели записываются фикстурами (`tests/fixtures/llm/`), прогон не ходит в сеть и не тратит квоту. Фикстуры ещё предстоит записать.
- **Пропуск, а не ошибка:** документы с содержимым во вложении помечаются `skip` — вложения не читаются, это решение о скоупе. Без разметки честны только эксплуатационные прокси из `quality_summary()`: доли `degraded`, скрытых и правок (`edited_share`); `hallucination_flags` считает `needs_review` и всегда равно нулю.

## Как обрабатывать низкую уверенность

- **Вверх, а не вниз:** пограничная релевантность или низкая уверенность повышают приоритет на ступень, причина дописывается в `reasoning`.
- **Обрезанный контекст честно снижает уверенность:** документ длиннее `max_chars: 12000` уходит префиксом (не map-reduce — иначе ломаются `evidence_offsets`), `confidence` умножается на 0.7, в `reasoning` — пометка об обрезке.
- **Флаги вместо тишины:** `degraded` — карточка собрана без модели; `date_estimated` — дата взята не из публикации; обрезка видна по пониженному `confidence`. `needs_review` остался от S6 и никем не выставляется — «перепроверить» решает человек.
- **Один корректирующий ретрай:** невалидный по смыслу ответ возвращается модели с причиной; второй отказ — деградация, а не пустая карточка.

## Откуда берутся модели, какие данные и по чему выбираем

| Задача | Что используется | Откуда | Какие данные видит |
|---|---|---|---|
| S2–S5: тип, саммари, сущности, приоритет | GLM-5.3 (`glm-5.3:cloud`) | внешний API Ollama Cloud, ключ `OLLAMA_API_KEY` | профиль компании + заголовок, источник, дата и `norm_text` |
| S1: кластеризация | эмбеддинги `embeddinggemma` (768) | тот же клиент и ключ | заголовок + первые 2000 символов `norm_text` |
| S0, S1, разбор и проверка ответа, fail-safe | собственный код, правила | репозиторий | текст документа |
| Аварийный путь | экстрактивный лид | репозиторий | текст документа |

- **Обученных внутри моделей нет:** дообучение за скоупом 1.2; `torch`, `sentence-transformers` проект не заводит. Провайдер спрятан за `LLMProvider` / `EmbeddingProvider` — переезд на GigaChat, YandexGPT или self-hosted меняет одну реализацию и `model` в конфиге.
- **Технические метрики выбора:** латентность против бюджета 15 с, доля ответов с первого раза (иначе ретрай), доля деградаций, токены на карточку. Всё пишется в `llm_calls` — сравнение двух провайдеров сводится к двум прогонам.
- **Что модель не видит:** `analyst_note` не передаётся в промпт конструктивно; во внешний API уходит только публичный контент.
- **Воспроизводимость:** в каждой карточке `model_name`, `prompt_version`, `profile_version` — регресс промпта отличим от смены модели.

## Разметка исторических данных

- **Разметка ручная, по уже собранным документам** (759 после прогонов 03.09.2026, приток ~600 в сутки): аналитик проставляет эталонные `type` и `priority`, для 20 пишет эталонное саммари. Отдельной команды разметки нет — `jsonl` заполняется руками.
- **Разметчиков минимум двое, потому что бенчмарка нет:** расхождения не усредняются, а фиксируются как открытые вопросы к профилю компании.
- **Правки аналитика — естественный поток разметки:** `item_revisions` хранит поле, «было/стало», кто и когда. Это будущий датасет для калибровки промпта и для классической модели приоритета.
- **Заметки аналитика в датасет не идут:** `analyst_note` — внутреннее поле, не попадает ни в промпт, ни в выгрузку.
