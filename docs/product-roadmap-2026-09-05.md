# Карта продукта и roadmap — 2026-09-05

Основа — фактический код (`src/api/`, `src/services/`, `src/processing/`, `src/sources/`, `frontend/src/`), не README. Проект — личный/small-team: приоритет простым решениям без новой инфраструктуры.

## 1. Карта текущего функционала (факт по коду)

### Сбор данных (src/sources/, src/services/collection_service.py)
- **Работает:**
  - Коллектор с 7 типами источников: RSS (условный GET по ETag), HTML-скрайпер, sitemap (по `lastmod`), Telegram MTProto (свой логин-флоу: `telegram login/status/logout` в CLI, src/sources/telegram_mtproto.py), поиск Tavily (сохранённые запросы `tavily://search?...`), ручные документы, LLM-скрайпер (src/sources/scraper_*.py).
  - Планировщик per-source интервалов **без демона и cron** — тик спрашивает БД «кто due» (src/sources/scheduler.py:1-51); `status in ('active','error')` опрашиваются, `error` — метка здоровья, не пауза.
  - Режимы запуска: `collect --watch` (CLI), `POST /api/v1/collection/start|stop` (фоновый поток `CollectionWatcher` в процессе API, src/services/collection_service.py:79-160), `POST /collection/runs` (разовый цикл в фоне). Повторный запуск защищён лок-ом `_CYCLE_LOCK` (collection_service.py:41).
  - Пробирование источника до сохранения: `POST /sources/probe` — распознавание типа, превью, предупреждение о дубле.
  - Мягкое удаление источника с `purge_items` (прячет карточки, документы не трогает) и restore.
- **Полуфабрикаты:**
  - `POST /collection/start|stop|runs` существуют (src/api/routes/collection.py:20-48), но **frontend не вызывает их**: в StatusView кнопки «Обработать очередь ИИ» и «Запустить автоматический мониторинг» захардкожены `disabled` (frontend/src/components/StatusView.vue:17). Автосбор включается только вручную через API/CLI.
  - Watcher живёт в процессе API: рестарт API = мониторинг остановлен (main.py lifespan только останавливает watcher); «самозапуск при старте» нет.

### Обработка (src/processing/, src/services/processing_service.py)
- **Работает:**
  - Пайплайн S1–S5 одним structured-вызовом LLM: нормализация → дедуп (exact hash → SimHash по 3-граммам → cosine по эмбеддингам с блокингом, src/processing/dedup.py) → классификация/саммари/сущности/приоритет с evidence-offsets (src/processing/pipeline.py). Один вызов на кластер перепечаток.
  - Деградация без убийства ленты: LLM недоступен → extractive baseline с `degraded=True`, confidence 0.3 (pipeline.py:203-225).
  - Failsafe приоритета: пограничная релевантность/низкая уверенность **повышают** приоритет, никогда не понижают (pipeline.py:186-201).
  - Прогоны обработки: `POST /processing/runs` (202, BackgroundTasks), история прогонов `GET /processing/runs`, статус очереди `GET /processing`; брошенные при рестарте прогоны помечаются проваленными (main.py lifespan).
  - Перепрофилировка карточки `reprocess()` с уважением к ручным правкам (`manual_overrides`) и записью model_proposals (processing_service.py:639-713) — **доступна только из CLI** (`python -m src reprocess`); HTTP-эндпоинта нет.
  - Метрики качества: `quality_summary()` по llm_calls (латенси, токены, failures, деградации, доля правок) и gold-set оценка (high recall ≥ 0.95) — **только CLI** (`process --gold`, `quality`); API не отдаёт.
  - Профиль компании с версионированием (`profile.py`, `profile_versions` в БД) — влияет на приоритизацию; управление только CLI.
  - Ручное добавление материала с детекцией дублей (`code: possible_duplicate`) и `force`-оверрайдом; `run_llm=false` сохраняет документ в очередь.
- **Полуфабрикаты:**
  - `needs_review` (флаг «проверить аналитику») проставляется, показывается в UI тегом «Нужна проверка» (NewsFeed.vue:57), но **нет ни одного рабочего процесса вокруг него**: нет фильтра «только needs_review», нет кнопки «проверено», нет счётчика очереди проверки в статусе.
  - Обработка не связана со сбором: документы копятся в `unprocessed` до ручного `process` / `POST /processing/runs`. Автозапуска обработки после сбора нет (нет вызова processing_service.run из коллектора).

### Лента и карточки (src/api/routes/items.py, frontend)
- **Работает:** серверные фильтры (источник, тип, НПА-статус, приоритет, тег, даты, порядок), FTS5-поиск (title+summary, `q`), курсорная пагинация с fingerprint-защитой от смены фильтров, фасеты, bulk-видимость, hide/unhide/soft-delete/restore, **archive/unarchive** (routes/items.py:163-170 — в UI не используется), события НПА-хронологии (`POST /{id}/events` — в UI кнопка disabled с подписью «появится после обновления сервиса», ItemPanel.vue:62), заметки аналитика, история правок + revert полей модели, правки с `manual_overrides` и `edit_reason`.
- **Полуфабрикаты:** UI отстаёт от API: события НПА, архив и reprocess-кнопка не представлены в интерфейсе.

### Дайджест (src/services/feed_service.py:117-155, digest.py)
- **Работает:** срез по фильтрам ленты (скрытое и архив не выгружаются никогда), markdown/json, заметки аналитика опционально, лимит 200, редактирование тела перед экспортом и выгрузка файлом (frontend DigestView).
- **Полуфабрикаты:** дайджест — «срез, а не сущность» (не сохраняется, не отправляется): нет ни одной доставки (email/Telegram/файл по расписанию).

### Наблюдаемость
- **Работает:** `/health`, `/health/ready` (готовность с degraded-503), `/status` (stale_sources с ошибками), история опросов источника (`/sources/{id}/health`, 20 последних runs), история прогонов обработки в БД + CLI, `llm_calls` — полный лог вызовов (модель, токены, латенси, ошибки).
- **Полуфабрикаты:** все метрики качества и истории прогонов — только CLI; UI показывает только агрегаты «документов/материалов/ожидают».

## 2. Пользовательские сценарии и болевые точки

**Сценарий A. «Утренний обзор» (GR/PR-специалист).**
Открывает ленту → фильтрует high за сегодня → вручную жмёт «Обновить» → карточки, помеченные «Нужна проверка», находит глазами в общем списке → правит, скрывает, добавляет заметки.
Боли: (1) данные на момент открытия могли не собраться — автосбор включается только API-вызовом после каждого рестарта; (2) `needs_review` не имеет фильтра/очереди — «утренняя проверка» не сгруппирована; (3) если LLM был недоступен ночью, деградированные карточки так и остаются с baseline-саммари, пока кто-то не догадается перепрогнать.

**Сценарий B. «Дайджест руководителю» (еженедельно).**
Открывает DigestView → «За 7 дней» → сформировать → правит текст → экспорт файла → **вручную вставляет в письмо/чат**.
Боли: доставка полностью ручная; повторяемость (тот же срез каждую неделю) — заново те же клики; нет истории сгенерированных дайджестов («а что отправляли на прошлой неделе?»).

**Сценарий C. «Ведение реестра НПА» (GR).**
Открывает раздел НПА → по каждому акту вручную: добавить событие нельзя из UI (кнопка disabled, ItemPanel.vue:62) — только `python -m src npa-event ...`; изменение статуса НПА = CLI-команда.
Боль: единственная полностью ручная область продукта; бэкенд-эндпоинт `POST /items/{id}/events` готов, UI не подключён.

**Сценарий D. «Эксплуатация системы» (это же человек, small team).**
Следит за `/status`, жмёт «Опросить» на застрявшем источнике, смотрит историю опросов; запускает обработку: `POST /processing/runs` из Swagger или SSH+CLI `process`; смотрит качество: `make quality`.
Боли: (1) «Обработать очередь ИИ» в UI disabled — кнопка-заглушка, при этом эндпоинт с 202-ответом уже есть; (2) качество LLM видно только в терминале — аналитик, который правит галлюцинации, не видит, что деградаций стало 30%; (3) рестарт API тихо убивает автосбор — узнаётся по устаревшей ленте.

**Сценарий E. «Подключение нового источника» (периодически).**
Probe → создать → опросить → проверить. Работает хорошо end-to-end из UI. Мелкая боль: нельзя изменить URL/тип существующего источника (только через удаление+создание, SourcesPanel: «Изменение URL и типа пока недоступно»).

## 4. Приоритизированный roadmap

### Quick wins (неделя) — «подключить то, что уже построено»
1. **A3** «Обработать очередь ИИ» в UI (`POST /processing/runs` готов).
2. **A4** toggle автомониторинга в UI (`POST /collection/start|stop` готовы).
3. **I1** события НПА из UI (`POST /items/{id}/events` готов, кнопка в разметке).
4. **Q1** reprocess-кнопка карточки (service готов — 1 маршрут + кнопка).
5. **N3** фильтр/очередь needs_review (1 SQL-условие + чекбокс).
6. **N1** панель качества (`quality_summary()` готов — 1 маршрут).

Все шесть — включение существующей функциональности, ноль миграций, риск минимальный. Они закрывают три disabled-заглушки в UI, которые сегодня сообщают пользователю «появится после обновления сервиса».

### Средний срок (месяц)
7. **A1** автозапуск мониторинга при старте + **A2** автопрогон обработки после сбора — система становится «включил и забыл» (единственная точка с миграцией: флаг автосбора).
8. **N2** история прогонов в UI.
9. **C2** сохранение дайджестов + **Q2** массовый reprocess деградированных.
10. **C1** отправка дайджеста в Telegram (переиспользование MTProto-стека), затем **C3** расписание.

### Дальний горизонт (не подтверждены текущей болью, не в приоритетах)
- ML-переранжирование ленты и рекомендация источников (сейчас приоритизация решается failsafe-пайплайном — признаков потребности нет).
- Мультитенантность и авторизация (осознанно вне скоупа, single-user UI уже так устроен).
- Мобильное приложение (UI отзывчив, потребности не видно).
- Уведомления email/вебхуки (после C1 станет ясно, нужен ли второй канал).
- Автоматическое управление жизнью НПА (автодетект статусов из новостей) — сейчас ручной ввод событий закрывает сценарий.

## 5. Риски и зависимости

| Риск | Фичи | Мера |
|---|---|---|
| **Миграции схемы** | A1 (флаг автосбора — единственная колонка/таблица настроек), C2 (таблица `digests`) | Обе мономиграции; существующая схема миграций через `PRAGMA user_version` (database.py) их переживёт без даунтайпа |
| **Ломают контракты** | Q1/A3 (новые POST-маршруты — аддитивны, контракты не ломают); N3 добавляет параметр `needs_review` в FeedQuery — аддитивно | Ничего не ломается; новые параметры фильтра должны пройти тот же валидатор `_one_of` (queries.py) |
| **Инфраструктура** | A2 (обработка в тике сбора — без новых воркеров: тот же поток, но **риск длинного LLM-прогона в watcher-потоке**; сначала ограничить `max_new_per_run`) | C1/C3 — без очередей: отправка тоже фоновая задача в том же процессе; лимит на частоту, лок как в `_CYCLE_LOCK` |
| **Внешние зависимости** | C1/C3 — Telegram API (уже в проекте, но сессия настроена на **чтение**: отправка требует прав на конкретный чат — проверить на живом стенде до commit'а оценки M/L) | Q1/Q2 — LLM-провайдер: гонки не создаёт, т.к. reprocess идемпотентен и уважает manual_overrides |
| **Гонки** | A2 (сбор ∥ обработка на одной SQLite): WAL уже включён, но записывающие транзакции стоит разносить по времени тика | Порядок: сначала A1, потом A2 с малым `max_new_per_run` |
| **Скрытая зависимость UX** | N3 без фильтра degraded (Q2) — очередь проверки может копиться; ввести счётчик вместе с фильтром | Совместный релиз N3+счётчик |

Главная зависимость всего плана: **quick wins не требуют ничего кроме фронтенда и тонких маршрутов** — бэкенд к ним уже готов, что и делает их первыми.
