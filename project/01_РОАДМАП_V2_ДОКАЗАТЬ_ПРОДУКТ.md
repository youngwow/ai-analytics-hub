# Roadmap V2: доказать автоматический контур, затем продукт

> **Статус:** единственный активный roadmap после диагностики 6 сентября 2026 года
> **Основание:** [диагностика текущего состояния](./ЦИФРА/04_ДИАГНОСТИКА_ТЕКУЩЕГО_СОСТОЯНИЯ.md)
> **Цель:** получить проверенный автоматический агент, доказательно выбрать его внутренние механизмы и только затем проверять ценность с PR/GR.

## Правило движения

- `[ ]` — не начато;
- `[~]` — единственный текущий шаг;
- `[x]` — есть артефакт, результат и пройденный gate;
- `[!]` — заблокировано внешним условием.

Не добавляем новый benchmark, гипотезу или функцию без решения, которое изменится после результата. Не называем наличие runner проведённым экспериментом. Не подгоняем известный holdout.

## Граница текущей работы

Сейчас доказываем автоматический контур:

`источники → нормализованный документ → AI-карточка → при необходимости доресерч → событие или НПА → черновик дайджеста`

В B3 контур заканчивается **готовым черновиком дайджеста**. Ручная проверка, редактура и финальное утверждение PR/GR — следующий, отдельный слой продуктовых экспериментов.

## Общий порядок

1. Зафиксировать pipeline и переключаемые варианты.
2. Пересобрать и максимально проверить `B1` — только сбор и парсинг.
3. Пересобрать корзину `B2` на реальных форматах B1 и известных рисках.
4. На B2 улучшить промпты, сравнить два контура и три модели, выбрать компоненты.
5. Пересобрать и прогнать `B3` — весь автоматический pipeline до черновика дайджеста.
6. Зафиксировать выбранную архитектуру, подтверждённые и убитые гипотезы.
7. Отдельно провести RAT и продуктовые эксперименты с PR/GR или честным proxy-пользователем.
8. Сделать одну итерацию, заморозить доказательства и перейти к упаковке.

## Этап 1. Зафиксировать автоматический pipeline

**Цель:** определить стабильные входы и выходы этапов. Финальный вариант внутри этапов выбирают бенчмарки, а не архитектурная догадка.

- [~] Сверить фактический код с последовательностью ниже и составить точный список недостающих соединений.
- [ ] Зафиксировать единый контракт `RawDocument → PreparedDocument → SignalDraft → Object/Event/NPA → DraftDigest`.
- [ ] Реализовать варианты за одинаковыми интерфейсами, чтобы benchmark менял только одну переменную.
- [ ] Фиксировать `model`, `prompt_version`, `strategy`, время, ошибки и стоимость каждого вызова.

### Этапы и открытые варианты

| Этап | Базовый путь | Проверяемый вариант |
|---|---|---|
| Первичный анализ | один промпт создаёт карточку и роль/интерес | два этапа: карточка, затем отдельный интерес PR/GR — `A1` |
| Доресерч новости | только первичный материал | reasoning-агент с Tavily — `A2-news` |
| Доресерч НПА | официальный первичный документ и сохранённая история | Tavily находит связанные официальные версии, пояснения, обсуждения и контекст влияния — `A2-NPA` |
| Кандидаты события | полный доступный банк | embedding top-20, затем та же LLM — `A3` |
| Связь НПА | отдельный короткий контракт identity/stage | обязательная проверка качества, не новая продуктовая гипотеза |
| Дополнительный critic | выключен | `A4` уже убит для текущего main flow; не возвращать без нового класса ошибок |
| Черновик дайджеста | детерминированная сборка карточек | LLM-редактор не добавлять без доказанной проблемы baseline |

### Ограничение доресерча НПА

Доресерч может дополнить карточку связанными документами, версиями, пояснениями и контекстом влияния. Он не имеет права самостоятельно объявлять официальный статус, дату вступления или номер версии. Для этих полей истиной остаётся подтверждённый официальный источник; найденное поиском без него хранится как кандидат.

### Gate 1

- [ ] Все варианты запускаются на одинаковом входном контракте.
- [ ] Выключение доресерча, embeddings или второго этапа не ломает остальной pipeline.
- [ ] Промпты и версии воспроизводимы.

## Этап 2. B1 — доказать сбор и парсинг

**Граница:** только получение и техническая нормализация. Никакой оценки полезности материала для GS Labs.

### Что проверяем

- [ ] RSS/Atom.
- [ ] Telegram web-preview и выбранный fallback.
- [ ] HTML/list pages.
- [ ] Sitemap и вложенные sitemap.
- [ ] Открытые JSON API, если они входят в фактический набор источников.
- [ ] Tavily только как транспорт и формат ответа; смысловая ценность поиска проверяется позже.

### Сценарии

- [ ] первый запуск и backfill;
- [ ] повторный запуск без дублей;
- [ ] новые элементы после checkpoint/cursor;
- [ ] пропущенное окно и догон хвоста;
- [ ] 403/429/5xx, timeout, malformed и partial;
- [ ] изменение порядка, даты, URL и формата ответа;
- [ ] большой ответ без молчаливого обрезания;
- [ ] параллельность, rate limit и изоляция сбоя одного источника.

### Метрики и результат

- parse success и field completeness;
- количество найденных, новых, повторных, пропущенных и дефектных документов;
- сохранность источника, URL, published/collected time и оригинала;
- latency p50/p95 с обязательным размером выборки;
- throughput, retries, partial, recovery и стабильность fingerprint;
- таблица `адаптер × источник × сценарий × результат × ограничение`;
- сохранённые реальные raw/normalized артефакты для проектирования B2.

### Что закрывает B1

- `C0`: техническая жизнеспособность базового сбора;
- инженерные решения concurrency/retry/fallback;
- не закрывает `H1`, absolute recall, полезность Tavily и продуктовую ценность.

### Gate 2

- [ ] Каждый заявленный тип источника имеет успешный, отказной и повторный сценарий.
- [ ] Нет молчаливой потери или необъяснимого обрезания.
- [ ] Все цифры имеют знаменатель и воспроизводимый артефакт.

## Этап 3. B2 — построить доказательную корзину

**Граница:** отдельные AI-задачи на замороженных документах. Без оркестрации полного продукта.

### Принцип корзины

Корзина не называется статистически репрезентативной для промышленного потока. Это:

1. **Real-flow слой:** реальные форматы и материалы, полученные B1.
2. **Case-anchor слой:** примеры из кейса, чата, Q&A и Excel.
3. **Challenge слой:** опасные случаи, выведенные из задач конкретных промптов.
4. **Rare-safety слой:** явно маркированная синтетика для редких критичных ситуаций.

### Какие риски обязаны покрываться

- релевантное, нерелевантное, пограничное и неизвестное;
- PR, GR, оба направления и общий критичный слой;
- low/medium/high/critical с достаточным числом положительных примеров;
- даты, сроки, числа, атрибуция и неподтверждённая причинность;
- длинный, короткий, неполный и шумный вход;
- точные дубли, перефразирование, одно событие и разные мнения;
- похожая тема, но другое событие;
- новый НПА, известный НПА, новая версия, новая стадия и ложная связь;
- доресерч новости и НПА: полезное дополнение, шум, противоречие и отсутствие результата.

### Разделение данных

- [ ] `development` — только здесь улучшаются промпты;
- [ ] `validation` — здесь выбираются варианты;
- [ ] новый закрытый `holdout` — открывается после заморозки;
- [ ] второй человек проверяет critical, borderline, event и NPA gold; разногласия сохраняются.

### Gate 3

- [ ] Каждая строка корзины существует ради конкретного риска или реального потока.
- [ ] Нельзя угадать gold по искусственным словам-подсказкам.
- [ ] Exact quote и semantic support оцениваются отдельно.
- [ ] Распределения real-flow и challenge показываются отдельно.

## Этап 4. B2 — провести AI-эксперименты

### 4A. Разработка промптов

- [ ] Итеративно улучшать промпты только на `development`.
- [ ] Сохранять каждую версию, изменение, причину и результат.
- [ ] Дать каждой модели одинаковый заранее ограниченный бюджет настройки, чтобы не сравнивать хорошо настроенную GLM с чужими нулевыми промптами.
- [ ] Не использовать validation/holdout для ручной подгонки.

### 4B. Матрица `A1 × A5`: контур и модель

На одинаковом validation прогнать все шесть комбинаций двух контуров и трёх моделей:

- `glm-5.3-flash:cloud`;
- `deepseek-v4-flash:cloud`;
- `gpt-oss:120b-cloud`.

Для каждой — `one-pass` и `two-pass`. Это не даёт спутать эффект модели с эффектом контура. Смотрим не один общий score, а качество карточки, роли/интереса, evidence, риски, latency, provider failures и стоимость. Выбранную комбинацию замораживаем и только затем подтверждаем неизменными holdout-повторами. Safety-gates нельзя усреднить.

### 4C. Остальные компонентные проверки

- [ ] `A3`: full scan против embedding top-20 на банках нескольких размеров.
- [ ] Identity/stage НПА отдельными короткими контрактами.
- [ ] `A2-news` и `A2-NPA` сначала проверить компонентно: что research действительно добавляет подтверждённые сведения, а не шум.
- [ ] Для выбранной конфигурации сделать несколько неизменных holdout-повторов.

### Результат B2

- выбранный prompt family;
- выбранный one-pass/two-pass контур;
- выбранная из трёх модель;
- решение по full scan/embedding в заявленном масштабе;
- границы доресерча новости и НПА;
- качество по каждому проблемному классу;
- список убитых, подтверждённых и неразрешённых технических гипотез;
- честная review-policy для следующего этапа.

### Gate 4

- [ ] Конфигурация выбрана на validation, затем один раз подтверждена holdout.
- [ ] Ни один provider failure не спрятан средним значением.
- [ ] У каждого технического выбора есть контроль, метрика, правило решения и артефакт.

## Этап 5. B3 — проверить весь автоматический агент

**Граница:** от источников до готового черновика дайджеста. Человеческая редактура не входит.

### Что исполняется вместе

1. Сбор и checkpoint через выбранные B1-адаптеры.
2. Нормализация и сохранение оригинала.
3. Выбранная B2-модель и prompt-контур.
4. Доресерч новости или НПА по условию.
5. Связывание события либо жизненный цикл НПА.
6. Техническая валидация и review-флаг.
7. Формирование общей и адресной структуры.
8. Сборка короткого черновика дайджеста с источниками.

### EXP внутри B3

- [ ] `H1`: настоящий fixed / Tavily search / hybrid на одном окне и query budget; происхождение находки скрывается при разметке полезности.
- [ ] `A2-news`: один и тот же важный/неполный сигнал с доресерчем и без.
- [ ] `A2-NPA`: один и тот же НПА с поиском связанных официальных документов и без него.
- [ ] Проверка выбранного `A1/A3/A5` уже как частей общей цепочки, а не новое переобучение.
- [ ] Технические proxy `H3/H4/H5`: корректно ли сформированы события, адресные варианты и top layer.

### Метрики

- покрытие реального входа и задержка каждого этапа;
- фактическая и evidence-точность;
- релевантность, важность и critical safety;
- ложные/пропущенные объединения;
- корректность identity/stage/history НПА;
- полезные новые research-факты против шума;
- ошибки адресации и потери critical core;
- latency, стоимость, failures и доля review;
- целостность черновика дайджеста.

### Результат B3

- доказано, работает ли выбранная архитектура совместно;
- закрыты техническая часть `H1`, `A2-news`, `A2-NPA` и интеграционные границы выбранных механизмов;
- получены только proxy для пользовательской ценности `H2–H5`;
- сформирован список системных провалов для одной итерации.

### Gate 5

- [ ] B3 проходит через реальные контракты B1/B2, а не заранее подготовленный `agent_input` в обход системы.
- [ ] После исправлений используется свежая часть данных.
- [ ] B3 называется автоматическим техническим E2E, а не пользовательским пилотом.

## Этап 6. Зафиксировать выбранную архитектуру

- [ ] Обновить архитектуру только по решениям B1–B3.
- [ ] Для каждой развилки поставить `подтверждена / убита / неразрешена / ограничена масштабом`.
- [ ] Создать индекс `гипотеза → EXP → данные → run → метрика → решение → ограничение`.
- [ ] Не выдавать технический proxy за продуктовый результат.

### Ожидаемый итог

Мы знаем, какой способ сбора, prompt-контур, модель, доресерч и механизм связывания реально сильнее, а не просто реализованы в коде.

## Этап 7. Проверить ценность с человеком

### Сначала довести пользовательский контур

- [ ] Редактирование карточки и audit history.
- [ ] Подтверждение/исключение материалов и сборка версии выпуска.
- [ ] Поиск, обязательные фильтры, управление источниками и ручное добавление.
- [ ] История и подтверждение изменений НПА.
- [ ] Переключаемые представления, нужные для `H2–H5`.

Только здесь закрываются:

- главная ценностная гипотеза;
- `R0/RAT`: ручной анализ с нуля против доводки AI-черновика;
- `H2`: review-all / risk-only / no-review;
- `H3`: flat / exact dedup / events для человека;
- `H4`: общий / адресный выпуск;
- `H5`: full queue / top layer.

Нужны одинаковые входы, одинаковое назначение результата, активное время, исправления, открытия оригиналов, критичные пропуски и фактические ошибки. Если реального PR/GR нет, результат называется ограниченным usability-proxy, а не подтверждением кейсодателя.
