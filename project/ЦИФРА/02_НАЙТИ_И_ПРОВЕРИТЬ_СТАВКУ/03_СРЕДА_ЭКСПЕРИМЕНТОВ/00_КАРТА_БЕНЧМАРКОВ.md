# Единый план пересборки бенчмарков и EXP

> **Это единственный управляющий файл всей работы с B1–B4 и экспериментами.** Спецификации `01–04` объясняют устройство каждого бенчмарка, но статус, порядок и следующий шаг меняются только здесь.

## Зачем мы это делаем

Мы не просто запускаем несколько тестов. Мы хотим получить доказательную цепочку:

`реальные входы → сильная AI-конфигурация → работающий автоматический E2E → содержательно качественный продуктовый результат → честные ограничения`

По итогам должны появиться:

- поддержанные, убитые и неразрешённые гипотезы;
- выбранная конфигурация каждого спорного участка pipeline;
- воспроизводимые метрики и артефакты;
- честное объяснение, что проверено без пользователей, а что требует будущего пилота.

|---|---|---|---|

| [`B2 AI`](./02_B2_AI.md) | 119 материалов, свежий holdout, сравнение контуров/моделей и component EXP | достаточен для выбора review-first GLM-контура, не для автономной публикации | customer gold GS Labs |
| [`B3 Automated E2E`](./03_B3_E2E.md) | полный runtime, fixed/search/hybrid, research, scale 100/1k/10k и NPA-сценарии | доказывает совместную работу компонентов на synthetic-среде | поведение реальных PR/GR |

### 5. Провести EXP в B2 — `[x]`

**История, которую нельзя затирать:** первый v2-кандидат был честно отклонён: в каждом из трёх runs был provider failure, а importance был нестабилен. Два blind LLM-review затем показали существенный дефект исходного gold. Старые splits были раскрыты и больше не использовались как новый holdout.

**Текущий факт:** gold пересобран field-level, prompt/config заморожены, затем создан новый holdout v4. Три повтора v4 технически стабильны, но выявили недостаточное качество релевантности, ролей и event linking. Поэтому B2 закрыт решением, а не искусственным PASS: конфигурация допускается только как review-first кандидат для B3.

**Обязательное ядро:** сравнение двух контуров `A1`, трёх моделей `A5`, качество фактов/evidence, релевантности, важности, событий и НПА. Без этого нельзя выбирать AI-конфигурацию.

**Вторичные развилки:** `A2/A3/A4` проверяются только если соответствующий механизм действительно входит в собираемый runtime и отрицательный результат изменит решение. Ради количества экспериментов их не раздуваем.

| EXP | Сравнение | Что решаем |
|---|---|---|
| `A1` | один prompt: карточка+роль / два prompt: карточка, затем PR/GR | какой контур анализа оставить |
| `A5` | `glm-5.3-flash:cloud` / `deepseek-v4-flash:cloud` / `gpt-oss:120b-cloud` | какую модель оставить при равном бюджете настройки |
| `A2-news` | первичный материал / reasoning+Tavily | нужен ли доресерч новости и по какому условию |
| `A2-NPA` | официальный первичный материал / Tavily-добор связанных документов | нужен ли доресерч НПА, не подменяя официальный статус |
| `A3` | полный банк / embedding top-20 + та же LLM | сокращать ли кандидатов embeddings |
| `A4` | без critic / с LLM-critic | даёт ли critic полезный прирост; старый отрицательный run не затирается |
| NPA quality | identity / relation / stage / version | проходит ли обязательный NPA-контракт |

Порядок:

1. Улучшать prompt только на development и дать трём моделям одинаковый бюджет настройки.
2. На validation сравнить матрицу `2 контура A1 × 3 модели A5`.
3. На победителе проверить NPA-контракты и только актуальные для runtime `A2/A3/A4`.
4. Заморозить итоговую конфигурацию.
5. Выполнить три неизменных holdout-повтора.

**Результат:** выбранные model/prompt/strategy, известные ошибки, review-policy и список поддержанных/убитых/неразрешённых технических гипотез.

**Факт закрытия:** матрица `A1×A5`, проверки `A3/A4`, gold-аудит и три неизменных запуска свежего holdout выполнены. Выбрана конфигурация `one_pass + GLM + full_scan + without_critic`; она прошла техническую стабильность без failed calls, но не принята для автономного выпуска: релевантность `8–9/19`, роли `10–11/19`, важность `12–13/18`, найдено `1–2/3` связанных пар событий. Архитектурное решение — review-first. `A2` осознанно переносится в B3, где доресерч можно сравнить на полном одинаковом потоке. Решение: `artifacts/b2/B2_V4_DECISION.md`.

### 6. Прогнать B3 через настоящий runtime — `[x]`

- удобство, доверие, понимание и внедрение;
- соответствие неизвестной внутренней рубрике GS Labs сверх доступной фактуры.

Это не прячем. Следующий честный шаг после хакатона — пилот с PR/GR на одном и том же потоке и ручном baseline.

## Общие правила

- старые версии и отрицательные результаты не затираются;
- сценарии, gold, пороги и решения фиксируются до run;
- real-flow, case-anchor, challenge, rare-safety и holdout считаются отдельно;
- tested system не видит gold и judge-инструкции;
- judge не должен быть моделью оцениваемого варианта, иначе это зависимый proxy;
- ни один средний score не перекрывает critical miss, unsupported claim, ложный статус НПА или потерю самостоятельной позиции;
- новый EXP появляется только если его отрицательный результат изменит продукт или архитектуру.

## Сила разных частей B4

- **Сильная объективная проверка:** сохранность фактов, дат, чисел и источников; event merge/split; identity/stage/version НПА; пропуск critical, заданного в gold.
- **Контекстный proxy:** релевантность GS Labs, важность, PR/GR/recipient fit и достаточность короткой повестки. Они зависят от полноты нашей реконструкции.
- **Не проверяется без людей:** фактическое время, удобство, доверие, понимание, ручная очистка и принятие продукта.
