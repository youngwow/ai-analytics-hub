Ниже — набор сборщиков, который стоит закладывать в архитектуру. Ключевая мысль: не делать 10 отдельных парсеров, а сделать **один резолвер типа источника** + набор адаптеров под общим интерфейсом.

## 0. Резолвер источника (то, что закрывает требование 1.4)

Пользователь вводит просто URL. Система сама определяет, чем его тянуть:

1. URL уже похож на фид (`.xml`, `/rss`, `/feed`) → RSS-адаптер
2. `t.me/...` → Telegram-адаптер
3. Иначе тянем HTML и ищем `<link rel="alternate" type="application/rss+xml">` — у большинства СМИ фид есть, но не афишируется
4. Нет фида → пробуем `/sitemap.xml` (там есть `lastmod`, можно ходить по нему как по ленте)
5. Ничего не нашли → generic HTML-краулер + diff по хешу

Это дёшево в реализации и на демо выглядит сильно: вставил ссылку — заработало.

## 1. СМИ и агрегаторы

**RSS/Atom** — `feedparser`, база. Ведомости, Коммерсант, РИА, ТАСС, Интерфакс, CNews, Кабельщик, Телеспутник — почти у всех есть ленты. Обязательно поддержать conditional GET (`ETag` / `If-Modified-Since`), иначе на каждом тике качаете всё заново.

**Извлечение полного текста.** В RSS часто только анонс. Тут лучший инструмент — `trafilatura`: она вытаскивает основной текст статьи из произвольного HTML, хорошо работает с русским, умеет и в фиды, и в sitemap. Альтернативы: `readability-lxml`, `goose3`.

**Sitemap-краулинг** для сайтов без RSS: раз в N минут тянем `sitemap.xml`, берём записи с `lastmod` свежее последнего запуска.

## 2. НПА и регуляторы

Это самая ценная и самая муторная часть — там же и жизненный цикл законопроекта, про который спрашивали на Q&A.

- **СОЗД Госдумы** (`sozd.duma.gov.ru`) — карточка законопроекта со стадиями, версиями текста, отзывами. Главный источник для «отслеживаемых» сущностей. У Думы есть публичный API (требует регистрации ключа), плюс сама карточка отдаётся достаточно структурированным HTML. Проверьте оба пути, начните с того, что заведётся быстрее.
- **regulation.gov.ru** — проекты НПА на стадии обсуждения, то есть самая ранняя точка, где ещё можно лоббировать. Ровно то, о чём говорила Ирина.
- **publication.pravo.gov.ru** — официальное опубликование, есть машиночитаемый доступ и разбивка по блокам/органам.
- **government.ru**, **cbr.ru**, **digital.gov.ru**, **rkn.gov.ru** — у большинства есть RSS или хотя бы предсказуемые списки.
- **Обзоры КонсультантПлюс / Гарант** — RSS, дают человекочитаемое «что изменилось».

К каждому НПА почти всегда идёт **пояснительная записка** — на Q&A прямо сказали, что её обычно достаточно вместо тела закона. Тяните её отдельным полем, это резко улучшит саммари.

## 3. Telegram

Три варианта, по убыванию мощности:

**MTProto через Telethon / Pyrogram** — user-сессия с `api_id`/`api_hash` с my.telegram.org. Читает историю любого публичного канала, умеет подписываться на апдейты (реальный push, а не поллинг), достаёт медиа и вложенные PDF-дайджесты. Это правильный вариант для продакшена и он реально даёт «15 минут до ленты».

**Веб-превью `t.me/s/<channel>`** — публичная HTML-страница канала, парсится обычным `httpx` + `selectolax`, вообще без авторизации и без риска словить бан аккаунта. Для хакатона — лучший старт: работает за 20 минут, покрывает все каналы из списка кейса.

**RSSHub** (`/telegram/channel/:username`) — если хочется свести Telegram к тому же RSS-адаптеру. Публичные инстансы нестабильны, но self-host в docker поднимается быстро. Бонус: RSSHub даёт ленты для кучи сайтов, у которых их нет.

## 4. LLM-поиск как отдельный слой

Важно не путать две задачи: **регулярный сбор** (крон по известным источникам) и **поиск по запросу** (ищем то, чего нет в подписках). Второе — это как раз Tavily / Perplexity Sonar / Exa / Brave Search API / Yandex Search API.

Где это реально полезно:

- **Discovery источников**: пользователь пишет «мониторь льготы для ИТ-компаний» → LLM-поиск возвращает 20 URL → резолвер превращает их в постоянные источники. Очень сильная демка.
- **Обогащение карточки**: нашли законопроект в одном канале → ищем, кто ещё о нём писал, подтягиваем мнения и отзывы. Это ровно тот сценарий «10 новостей про КИИ не схлопывать, интересно кто что пишет».
- **Закрытие дыр**: сайт лёг, парсер сломался — фоллбэк на поиск.

Оговорка по российской специфике, её прямо озвучили на Q&A: западные search-API плохо достают `gov.ru` и профильные российские домены. Так что LLM-поиск — это дополнение, а не замена RSS+Telegram, и стоит посмотреть в сторону Yandex Search API (XML-поиск) для доменов регуляторов.

## 5. Что ещё

- **Ручной ввод** (требование 1.4) — трактуйте как источник типа `manual`, тогда он ложится в ту же модель без спецкейсов.
- **Вставка произвольной ссылки** «прочитай вот это» → trafilatura + LLM, одноразовый импорт.

## Нормализация и общая обвязка

Все адаптеры возвращают один `RawDocument`: `source_id, external_id, url, title, published_at, fetched_at, raw_html, text, attachments, author`.
